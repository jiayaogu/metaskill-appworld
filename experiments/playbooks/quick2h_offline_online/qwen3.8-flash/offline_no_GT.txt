## STRATEGIES AND HARD RULES
[shr-00001] Make sure to end code blocks with ``` followed by a newline(\n).
[shr-00005] Always look at API specifications (using apis.api_docs.show_api_doc) before calling an API.
[shr-00006] Write small chunks of code and only one chunk of code in every step. Make sure everything is working correctly before making any irreversible change.

[shr-00009] For bulk destructive operations, derive the target set from documented authoritative fields and verify the final state by re-querying affected objects and recomputing the predicate; never rely on cached maps or undocumented response fields.
[shr-00020] Match the requested output format exactly. If the task asks for comma-separated titles in a message, send only the comma-separated list (or the exact requested phrasing), not extra prose or labels.
[shr-00025] Do not redefine the task predicate when no candidate satisfies it. Treat a zero-result authoritative constraint as a signal to exhaust all relevant sources or create the required object; only fall back to a weaker interpretation if the task explicitly permits it. If creation is not allowed and no candidate satisfies the constraint, report infeasibility instead of performing the action on a near-miss.
[shr-00048] For any bulk mutation, including non-destructive operations such as follow, like, add, or remove, derive target_ids from a computed predicate and execute by iterating over target_ids. Never hardcode a single ID or manually selected candidate, even if the printed result appears to contain only one qualifying item; 'all' requires programmatic handling of the whole target set.
[shr-00054] For genre+threshold follow tasks, enumerate the full genre universe with search_artists(genre=..., page_index/page_limit) without relying solely on min_follower_count; then compute target_ids from authoritative show_artist follower_count and follow all target_ids programmatically.
[shr-00056] For bulk follow/enumeration tasks, do not use try/except fallbacks that replace authoritative lookup failures with guessed values; if an authoritative endpoint such as show_genres, search_artists, or show_artist fails, stop and debug before any mutation.
[shr-00061] For bulk approvals filtered by personal relationships, derive target_request_ids from authoritative contact relationship fields and email matching, not from Venmo sender names, transaction descriptions, or friendship status. If a pending sender's name matches a target contact name but its email is not in target_emails, stop and reconcile the identity/email mismatch before mutating; do not silently approve by name or silently exclude without checking.
[shr-00065] For Venmo 'reject' or 'deny' bulk tasks, treat reject as a status change via venmo.deny_payment_request, not venmo.delete_payment_request. Derive target_request_ids from pending status and authoritative phone relationships/email matching, deduplicate them, and abort before mutation if any authoritative list/pagination response is a failure dict; do not continue with partial snapshots.
[shr-00069] For Venmo relationship-filtered approvals, treat any authoritative list/pagination failure (pending, approved, or phone contacts) as fatal: abort before mutation and do not break out of pagination and continue with a partial snapshot.
## APIs TO USE FOR SPECIFIC INFORMATION
[api-00004] You can use the "supervisor" app to get information about my accounts and use the "phone" app to get information about friends and family.

[api-00010] Spotify year filtering: show_song_library returns song_id but not release_date; use show_song(song_id) to get release_date as an ISO string. For playlists, inspect show_playlist_library response schema; if it does not guarantee song_ids, call show_playlist(playlist_id) and use songs[].id as the authoritative song IDs.
[api-00014] Spotify removal APIs return message objects, not booleans/lists: remove_song_from_library(song_id, access_token) returns {'message': 'Song removed from library.'} on success, and remove_song_from_playlist(playlist_id, song_id, access_token) returns {'message': 'Song removed from playlist.'}; check the current doc before assuming response shape.
[api-00024] Simple Note: search_notes returns note metadata (e.g., note_id, title, tags) but not full content; call show_note(note_id) to retrieve content. Paginate search_notes and other search/list endpoints rather than assuming one page contains all results.
[api-00026] Spotify timed-playlist selection: show_song.duration is in seconds, so required_seconds = workout duration_mins * 60. Enumerate all authoritative playlist sources (show_playlist_library, show_liked_playlists, search_playlists) and compute totals from show_playlist songs[].id. If no existing playlist meets the duration, check docs for create_playlist and add_song_to_playlist, create a new playlist, add songs until the summed duration is sufficient, then verify before play_music.
[api-00031] Spotify mutation/playback schemas: add_song_to_playlist returns a message object (observed success may be {'message': 'Song added to the playlist.'}), not a boolean or list; create_playlist returns {'message', 'playlist_id'}; play_music returns {'message', 'song_id'}; show_current_song returns {'song_id', 'is_playing', ...}. Do not hardcode exact success strings; verify mutations by re-querying show_playlist/show_song.
[api-00037] file_system path listings and compression schemas: show_directory returns a list of absolute path strings; directory entries end with '/', file entries do not. Use entry_type='directories' or 'files' and recursive=False for immediate children; use recursive=True for snapshots. compress_directory returns {'message', 'compressed_file_path'} on success and has delete_directory and overwrite parameters (defaults false); a success message or file_exists only proves an archive was written, not that it contains the expected files. Before decompressing or creating temporary verification directories, check show_api_doc for decompress_file and create_directory.
[api-00041] file_system response path normalization: show_directory success returns a list of absolute path strings, while failure returns a dict with 'message'. compress_directory and decompress_file success return dicts with absolute compressed_file_path/decompressed_directory_path even when input paths use '~'. Before using these responses, assert the expected type and compare returned paths to the expected normalized/absolute path; do not rely only on success messages.
[api-00049] Spotify artist-following schemas: search_artists returns a paginated list of artist dicts containing artist_id, name, genre, and follower_count; show_artist returns a dict with authoritative follower_count; follow_artist returns a message dict such as {'message': 'Artist followed.'}; show_following_artists returns a paginated list of followed artist dicts containing artist_id. Use genre='classical' and paginate; cross-check follower_count via show_artist before following.
[api-00053] Spotify artist-following exact schemas and parameter discipline: supervisor.show_account_passwords returns a list of dicts with account_name and password; spotify.login success returns {'access_token', 'token_type'}; show_genres success returns a list of strings (use the exact genre value, e.g. 'EDM'); search_artists documented parameters are query, genre, min_follower_count, max_follower_count, page_index, page_limit, sort_by — do not pass access_token unless the current doc lists it; success returns a list of artist dicts with artist_id, name, genre, follower_count, created_at, and failure returns {'message'}; show_artist success returns a dict containing authoritative follower_count, failure returns {'message'}; follow_artist returns {'message'}; show_following_artists returns paginated followed artist dicts with artist_id and followed_at.
[api-00057] Spotify genre resolution and failure handling: show_genres returns a list of exact genre strings; search_artists genre must be one of these exact case-sensitive values. If show_genres fails, returns a dict/error, or the requested genre is absent, stop and debug/try documented alternatives; never silently fall back to a guessed casing such as 'reggae'.
[api-00060] Venmo/phone relationship-filtered approval schemas: supervisor.show_account_passwords returns a list of dicts with account_name and password; venmo.login returns {'access_token', 'token_type'}; venmo.show_received_payment_requests accepts status ('pending', 'approved', 'denied'), page_index, and page_limit and returns a list of dicts with payment_request_id, amount, description, sender.name, sender.email, receiver, and timestamps; venmo.approve_payment_request returns {'message'}; phone.login returns {'access_token', 'token_type'}; phone.search_contacts returns a list of contact dicts with email, phone_number, first_name, last_name, and relationships. Match Venmo sender.email to contact.email whose relationships include exact 'roommate'/'coworker'; verify by re-querying status lists.
[api-00066] Venmo denial and phone relationship schemas: venmo.deny_payment_request(payment_request_id, access_token) returns a dict with 'message' on success and also a dict with 'message' on failure, so the message alone is not proof; verify by re-querying pending/denied. venmo.show_received_payment_requests accepts status values 'pending', 'approved', 'denied'; page_limit defaults to 5 and max 20. phone.search_contacts returns relationships as exact strings; enumerate contacts and collect actual relationship values before filtering, and use exact 'friend' and 'roommate' for friends/roommates.
[api-00070] Venmo approval response schema: venmo.approve_payment_request returns a dict with 'message' on both success and failure, so the message alone is not proof. Assert isinstance(response, dict) and 'message' in response, then verify by re-querying pending/approved status lists.

## COMMON MISTAKES AND CORRECT STRATEGIES

[cms-00011] Do not assume list endpoints return nested IDs (e.g., show_playlist_library may or may not include song_ids). Check the API doc in the current task and fall back to detail endpoints before making irreversible removals.
[cms-00015] Do not reuse API schemas or optional parameter values from a previous task (e.g., assuming page_limit=20 for show_playlist_library). In a new environment, call show_api_doc for each list/detail/removal endpoint immediately before first use, including pagination parameters.
[cms-00016] Do not reuse cached library_song_details when deciding playlist removals. Fetch fresh show_song details for every playlist song at decision time, even if the song_id already appeared in the library, because bulk destructive operations require fresh authoritative fields.
[cms-00018] Use variables retrieved from the current environment for credentials and tokens (e.g., spotify_password and spotify_access_token) in subsequent calls; do not paste printed secret literals into later code blocks.
[cms-00019] If a parser or extraction returns [] or fails, treat it as a bug to debug against the full response variable, not as permission to hardcode from truncated console output. Inspect the complete content, fix the parser (e.g., preserve leading spaces before checking ' - ' or use regex), and verify the extracted result is non-empty and matches the source before sending or answering.
[cms-00021] Do not skip show_api_doc for seemingly simple endpoints such as supervisor.show_account_passwords, supervisor.complete_task, phone.send_text_message, simple_note.login/search_notes/show_note, or any list/search endpoint. Check parameters and response schemas before first use in each new environment.
[cms-00027] Do not stop pagination with an arbitrary cap such as page_index > 50. Loop until the page is empty or a documented failure/end is returned, and guard against dict error responses before extending results.
[cms-00030] Do not treat show_playlist_library and show_liked_playlists as the complete playlist universe for timed-playlist selection. Before creating a new playlist, call show_api_doc for search_playlists, paginate it (query='' if accepted or relevant workout queries), deduplicate playlist_id, and evaluate every unique candidate via show_playlist and fresh show_song durations. If any existing playlist meets required_seconds, play it instead of creating one.
[cms-00034] Do not stop timed-playlist selection after finding a sufficient playlist in show_playlist_library or show_liked_playlists. The phrase 'a playlist on Spotify' includes public/searchable playlists, so actually call and paginate search_playlists (query='' and/or workout/fitness queries) before choosing any playlist; deduplicate playlist_id across all three executed sources and evaluate every unique candidate. Checking show_api_doc for search_playlists is not a substitute for executing it.
[cms-00039] Do not treat compress_directory success, file_exists, or presence of a .zip file as sufficient verification before deleting source directories; archives can be empty, incomplete, or misnamed. Do not pass overwrite=True by default; check whether the target archive already exists and only overwrite if the task permits it or after preserving/choosing a safe path.
[cms-00042] Do not use manually counted file numbers or eyeballed directory contents for destructive file-system verification. Derive expected file sets and counts programmatically from authoritative recursive show_directory output, store them in variables, and compare decompressed archive basenames or normalized relative paths to those variables before deleting source directories.
[cms-00044] For file_system destructive workflows, do not rely on printed success messages for mutations. Assert response schemas and absolute paths for decompress_file and delete_directory: decompress_file should return a dict with the expected absolute decompressed_directory_path, and delete_directory should return a dict; confirm deletion by re-querying the path rather than trusting the message alone.
[cms-00052] Do not manually copy IDs, titles, or final answers from printed console output even when the full source content is visible. If parsing returns [] or mismatches, debug the parser against the full response variable or use documented authoritative fields, store results in variables, and construct outputs programmatically (e.g., ', '.join(titles)); assert non-empty and expected count before sending or completing.
[cms-00058] Do not stop pagination when a page contains no new IDs. Deduplicate IDs but continue until the page is empty or a documented end condition is reached; overlapping pages or ignored page_index can otherwise cause missed targets. Also omit optional pagination parameters such as page_limit unless the current doc requires them or you intentionally set them.
[cms-00063] Do not skip show_api_doc for authentication/credential endpoints in a new environment, including venmo.login, phone.login, simple_note.login, supervisor.show_account_passwords, and supervisor.complete_task. Even if a login schema was seen in a prior task, re-check parameters and response schemas before first use.
[cms-00067] Do not use direct indexing such as r['sender']['email'] when sender or email may be missing; use .get and reconcile missing emails before mutating. Do not reconcile identity only by exact first+last name; compare normalized names, emails, phone numbers, contact IDs, and Venmo profile fields, and stop to resolve near-name/email mismatches before bulk denials/approvals.
[cms-00072] Do not reuse a roommate/coworker filter for a coworker+friend Venmo approval task. Enumerate actual phone relationship values and filter exact 'coworker' or 'friend' (or the relationships explicitly requested); match Venmo sender.email to those contacts, not sender names.
