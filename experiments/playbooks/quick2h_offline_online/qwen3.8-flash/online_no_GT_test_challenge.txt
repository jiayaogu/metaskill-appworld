## STRATEGIES AND HARD RULES
[shr-00001] Make sure to end code blocks with ``` followed by a newline(\n).
[shr-00005] Always look at API specifications (using apis.api_docs.show_api_doc) before calling an API.
[shr-00006] Write small chunks of code and only one chunk of code in every step. Make sure everything is working correctly before making any irreversible change.

[shr-00009] When an API operates on an entire mutable collection (e.g., Amazon place_order orders all cart items), isolate target items using the least destructive available mechanism (e.g., move unrelated items to wishlist) rather than deleting them, unless deletion is explicitly requested.
[shr-00018] Before a multi-API workflow, enumerate every API you will call and fetch show_api_doc for each, including auxiliary list APIs (e.g., show_payment_cards, show_addresses), messaging APIs, and complete_task; do not assume parameters, return shape, or pagination.
[shr-00059] Do not assume standard-library modules are available. If `base64` is blocked, stop using it; probe globals for `env_date`/`jwt_exp`, or decode a JWT payload manually with a custom base64url decoder and parse `exp` with `json.loads`.
[shr-00069] For scheduled future communications, compute the next occurrence using both the current date/time and the required send time, not just the calendar date. If the event date is today, schedule only if the send timestamp is not before now; otherwise roll to the next year. For Feb 29 birthdays, use a safe fallback such as Feb 28 in non-leap years instead of constructing `datetime.date(year, 2, 29)` unguarded.
[shr-00070] When recipients have different scheduled dates, create one scheduled draft per recipient. Do not batch all recipients into a single draft because Gmail scheduling is per-draft and each birthday requires its own future timestamp.
[shr-00075] Treat each task/environment as fresh for API documentation: maintain a per-environment doc-fetch manifest and call show_api_doc before the first use of every API in that environment, even if the same API was documented in a previous task.
## APIs TO USE FOR SPECIFIC INFORMATION
[api-00004] You can use the "supervisor" app to get information about my accounts and use the "phone" app to get information about friends and family.

[api-00010] Amazon cart/order schemas: apis.amazon.show_cart returns a dict with cart_items, not a bare list; apis.amazon.show_product returns a dict containing product_type; apis.amazon.place_order requires payment_card_id and address_id and orders all items currently in the cart.
[api-00015] Amazon isolation/payment schemas: apis.amazon.move_product_from_cart_to_wish_list has quantity default=1, so pass each cart item's full quantity; apis.amazon.show_payment_cards returns expiry_month/expiry_year, and first valid means first unexpired card relative to current date, not first returned.
[api-00019] Simple Note/Phone schemas: apis.simple_note.search_notes returns note metadata only, not content; apis.simple_note.show_note returns a dict with a content string; apis.phone.search_text_messages returns a list of message dicts; apis.phone.send_text_message returns a dict containing text_message_id.
[api-00020] Amazon order/isolation schemas: apis.amazon.place_order requires access_token in addition to payment_card_id and address_id and returns a dict with order_id; apis.amazon.move_product_from_cart_to_wish_list returns a dict with message; apis.amazon.show_payment_cards and apis.amazon.show_addresses return lists of dicts with payment_card_id/address_id and may be paginated.
[api-00026] Venmo transaction/comment schemas: apis.venmo.show_transactions returns a list of transaction dicts with transaction_id, amount, description, sender/receiver dicts containing email, and supports direction='received', user_email, page_index; apis.venmo.show_transaction_comments returns a list of comment dicts; apis.venmo.create_transaction_comment returns a dict with comment_id and message.
[api-00027] Amazon search/order schemas: apis.amazon.search_products returns a list of product dicts with product_id, product_type, name, price, inventory_quantity and is paginated; apis.amazon.place_order success requires a dict containing order_id, while expired-card failures may raise 422 or return a failure dict, so do not treat absence of exception as success.
[api-00037] Simple Note pagination: `apis.simple_note.search_notes` supports `page_index` and returns note metadata only; loop all pages to collect every matching `note_id`, then call `apis.simple_note.show_note` for each note before parsing content.
[api-00043] Amazon Prime payment-card lookup schemas: `apis.amazon.show_prime_subscriptions` returns a list of dicts with `prime_subscription_id`, `start_date`, `end_date`, `payment_card_digits`, and `paid_amount`; it supports `page_index`/`page_limit` and does not return card name. `apis.amazon.show_payment_cards` returns dicts with `card_name` and `card_number` (may be numeric/float); match `payment_card_digits` to the last four digits of `card_number` as strings.
[api-00044] Supervisor credential schema: `apis.supervisor.show_account_passwords` returns a list of dicts with `account_name` and `password`; fetch its `show_api_doc` before first use and extract passwords programmatically rather than assuming the shape.
[api-00048] Spotify premium payment-card lookup schemas: `apis.spotify.show_premium_subscriptions` returns a list of dicts with `premium_subscription_id`, `start_date`, `end_date`, `payment_card_digits` (string), and `paid_amount`; it supports `page_index`/`page_limit` and does not return card name. `apis.spotify.show_payment_cards` returns dicts with `card_name` and `card_number` (may be numeric/float) but may omit cards used in historical subscriptions. `apis.supervisor.show_payment_cards` returns the master list with `card_name` and `card_number` (may be numeric/float) and takes no parameters; match masked digits to the last four digits of `card_number` as strings.
[api-00053] Gmail/file_system download schemas: `apis.gmail.show_inbox_threads` supports `query`, `attachment=True`, `page_index`, and `page_limit`; `apis.gmail.show_email` returns `attachments` as a list of dicts with `id` and `file_name`; `apis.gmail.download_attachment` requires `attachment_id`, Gmail `access_token`, and `file_system_access_token`, optionally accepts `download_to_file_path` (defaults to `~/downloads`), and returns a dict with `message` and `file_path`. `apis.file_system.login` uses the supervisor email as username and returns `access_token`.
[api-00058] Gmail/file_system download path schema: `apis.gmail.download_attachment.download_to_file_path` must include the final filename and extension (e.g., `~/documents/personal/ticket_c7e6329.pdf`), not just the target directory; directory-only paths raise 422. Ensure the target directory exists with `apis.file_system.create_directory(..., recursive=True)` and verify with `apis.file_system.file_exists(file_path=..., access_token=...)`, which returns `{'exists': bool}`.
[api-00063] Gmail thread/download schema: `apis.gmail.show_inbox_threads` returns dicts with `email_thread_id`, `subject`, and `email_ids` (a list of email IDs); use `email_ids` for `apis.gmail.show_email`, not `email_thread_id`. `apis.gmail.download_attachment` returns `file_path` as an absolute path (e.g., `/home/user/documents/work/ticket.pdf`) even when `download_to_file_path` uses `~/...`; assert by suffix/expanduser and use the returned absolute path for `apis.file_system.file_exists`.
[api-00067] Phone birthday-scheduling schemas: `apis.phone.get_current_date_and_time` takes no parameters and returns `date` in human format (e.g. `Thursday, May 18, 2023`) and `time` (e.g. `12:00 PM`); parse them together with `%A, %B %d, %Y %I:%M %p`. `apis.phone.show_contact_relationships` returns exact relationship labels, and `apis.phone.search_contacts` supports `relationship='friend'`, `page_index`, and `page_limit`, returning contact dicts with `contact_id`, `email`, `birthday`, and `relationships`.
[api-00068] Gmail scheduled-draft schemas: `apis.gmail.create_draft` requires `recipient_email_addresses` as a list, `body`, and `access_token`; optional `subject`; and supports `scheduled_send_at` in `YYYY-MM-DD|HH:MM:SS`. Success returns a dict containing `draft_id`. `apis.gmail.show_draft` returns `scheduled_send_at` normalized to `YYYY-MM-DDTHH:MM:SS`, plus `recipients`, `subject`, and `body`. `apis.gmail.show_category_sizes` returns `scheduled_drafts` as an integer count.
[api-00076] Gmail show_draft verification schema: `apis.gmail.show_draft` returns `recipients` as a list of dicts with `email`/`name`, not a list of strings; compare `[r['email'] for r in recipients]`. Its `scheduled_send_at` is normalized to `YYYY-MM-DDTHH:MM:SS`, so when verifying a draft created with `YYYY-MM-DD|HH:MM:SS`, replace `|` with `T` before equality checks.
[api-00079] Phone/Gmail login username schemas: `apis.phone.login` requires `username` equal to the supervisor phone number; `apis.gmail.login` requires `username` equal to the supervisor email. Passwords come from `apis.supervisor.show_account_passwords` by `account_name`.

## COMMON MISTAKES AND CORRECT STRATEGIES

[cms-00011] Classify products by the authoritative product_type field from show_product, not by product-name keywords; for example, a workbench is not a weightlifting bench.
[cms-00012] When a task does not specify a payment card or address, use the first valid/default item returned by show_payment_cards/show_addresses instead of unstated heuristics such as latest expiry or Home vs Work.
[cms-00016] Derive target product IDs programmatically from the authoritative product_type mapping, e.g. target_ids = {pid for pid, ptype in product_types.items() if ptype == 'beach ball'}, instead of hardcoding IDs read from printed output.
[cms-00021] When parsing free-text note content, normalize whitespace and bullet prefixes (e.g., line.lstrip('- ').strip()) and match fields by substring/regex; if extraction returns empty but raw content visibly contains matches, treat it as a parser bug and fix it—never manually copy values into the final answer/message.
[cms-00022] For tasks requiring a reply with comma-separated titles, send exactly ', '.join(titles) as the message body; no greeting, explanation, or extra prose.
[cms-00028] When a Venmo payment identifies the product, select the Amazon product programmatically: filter search_products results by exact normalized name and price equal to the payment amount, assert exactly one match, then verify with show_product; do not hardcode the top printed product_id.
[cms-00029] Resolve the Venmo payer from phone contacts by relationship (e.g., 'brother'/'sibling') and email, then filter received transactions programmatically by sender email, amount equal to product price, and description containing the product name or 'for me'; do not visually choose a transaction ID.
[cms-00030] If the task explicitly specifies an address type (e.g., home address), select the address whose name matches that type from show_addresses; use first/default only when the task does not specify.
[cms-00036] When parsing note-derived lists, normalize each raw line with `raw.strip().lstrip('- ').strip()` before classification; do not test `startswith(' - ')` after stripping because it removes the leading space and misclassifies metadata lines as titles. Before sending, assert the extracted list is non-empty and every extracted title appears in the raw note content; if not, debug the parser rather than manually copying values.
[cms-00038] If multiple Venmo payments from the same sender identify different errands, select the transaction whose description matches the task beneficiary (e.g., 'for me' for the sister herself, not 'for parents') and confirm with product name/amount; do not choose the first, largest, or most recent transaction without this disambiguation.
[cms-00041] Do not treat Venmo/Amazon transaction `created_at` as the current date when selecting the first valid payment card; it is only an event timestamp. Use an actual system/environment date if available; otherwise iterate cards in returned order with try/except and accept only a response containing `order_id`.
[cms-00046] Do not hardcode the final answer literal from printed output; for information tasks, pass the computed variable to `apis.supervisor.complete_task(answer=card_name)` (or equivalent), not `answer='Wells Fargo'` or a manually copied string.
[cms-00049] Do not conclude that no matching card exists when `apis.spotify.show_payment_cards` lacks the subscription's last-four digits; app-specific saved cards may be incomplete. Fall back to `apis.supervisor.show_payment_cards` as the authoritative master card list, and if needed download the latest premium receipt (`apis.spotify.download_premium_subscription_receipt` + `apis.file_system.show_file`) to confirm `payment_card_digits` before matching.
[cms-00054] For email attachment downloads, do not rely on Gmail query ranking or printed top results; collect candidate threads with `attachment=True` and subject filters, then parse `show_email` body/attachments programmatically. Select the target email and attachment from authoritative fields, not visual inspection. When both receipt and ticket attachments exist, filter by filename patterns such as `file_name.startswith('ticket_')` and assert exactly one matching email and one matching attachment before calling `download_attachment`; never hardcode an `attachment_id`.
[cms-00061] For flight-ticket Gmail searches, do not rely on destination-only queries such as `query='Santorini'`; collect `attachment=True` threads and filter by authoritative subject/body fields (e.g., `Flight Confirmation`, destination, and flight date), because query ranking can return many irrelevant threads.
[cms-00064] For Gmail email workflows, never hardcode `email_ids` or `attachment_ids` from printed thread/email output. Collect candidate `email_ids` programmatically from all paginated `show_inbox_threads` results by filtering authoritative `subject` metadata (e.g., flight confirmation regex), then fetch `show_email` for each and select the attachment from parsed `file_name`/body/date fields with assertions.
[cms-00071] Do not assume there are zero pre-existing scheduled drafts or that repeated runs are idempotent. Baseline `apis.gmail.show_category_sizes`, deduplicate contacts by `contact_id` or normalized email, skip or explicitly handle missing `email`/`birthday`, and verify that final `scheduled_drafts` increases by exactly the number of newly created drafts.
[cms-00072] Do not use date-only logic for birthday scheduling; a friend whose birthday is today can produce a past `scheduled_send_at` if the current time is already after the required send time. Always compare the full candidate datetime against the current datetime.
[cms-00078] Do not reuse example send times from templates; for scheduled birthday emails, set `send_time` to the task's required time (e.g., `datetime.time(0, 45)` for 00:45 AM) and format `scheduled_send_at` as `YYYY-MM-DD|HH:MM:SS` for `apis.gmail.create_draft`.
[cms-00080] For per-recipient scheduled emails, deduplicate by `contact_id` and by `(normalized_email, scheduled_send_at)`; do not drop distinct friends who share an email but have different birthdays. Do not silently skip missing `email`/`birthday`; assert all intended recipients have both or explicitly log excluded `contact_id`s.

[misc-00008] Once you have completed the task, make sure to call apis.supervisor.complete_task(). If the task asked for some information, return it as the answer argument, i.e. call apis.supervisor.complete_task(answer=<answer>). Many tasks do not require an answer, so in those cases, just call apis.supervisor.complete_task() i.e. do not pass any argument.
