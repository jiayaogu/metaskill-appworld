## STRATEGIES AND HARD RULES
[shr-00001] Make sure to end code blocks with ``` followed by a newline(\n).
[shr-00005] Always look at API specifications (using apis.api_docs.show_api_doc) before calling an API.
[shr-00006] Write small chunks of code and only one chunk of code in every step. Make sure everything is working correctly before making any irreversible change.

[shr-00018] Call apis.api_docs.show_api_doc before the first use of every API in a task, even if the playbook already lists its schema; playbook hints are memory aids and do not replace checking the live spec for parameters and response fields.
[shr-00024] For tasks that depend on replies from specific people, resolve identity and provenance from the authoritative app: use apis.phone.search_contacts to get contacts whose relationships include the requested roles (e.g., roommate, friend), then query apis.phone.search_text_messages by each verified phone_number and filter by sent_at relative to the original inquiry. Do not rely only on keyword search (e.g., 'promo'), because it can include unrelated senders/old messages and miss replies that do not contain the keyword.
[shr-00046] REPL transactional guard: for irreversible cart mutations, do not split clear/add/place_order/restore across separate code blocks with independent try/except. Either execute the entire mutation-to-restoration sequence in one code block with one outer try/finally, or persist original_cart and a mutation_started flag and ensure every subsequent block restores on failure. A try/finally in a later block cannot undo a failure in an earlier block.
[shr-00054] Subscription card-name source hierarchy: for questions asking the card name used for a subscription payment, first resolve the subscription's payment_card_digits against the same app's payment-card list. Only use supervisor/global payment cards as a fallback after confirming the live API docs/description indicate that list contains the app's cards or deleted cards; receipts may confirm masked digits but not card names.
[shr-00059] Subscription card-name assertion sequencing: when resolving a subscription's payment_card_digits, do not assert a unique match on the app's active payment-card list before considering fallback. If the primary list has zero matches, treat it as a possible deleted/historical card and continue to the global supervisor card registry only after confirming its live docs/description support deleted/global cards; assert exactly one match and correct owner only on the final selected source.
[shr-00063] Email recipient role provenance: when a task says send to manager/family/etc., resolve the role from an authoritative source (apis.phone.search_contacts with relationship='manager' or supervisor profile if exposed) and assert the draft recipient matches; if mismatched, pass email_addresses in update_draft. Do not assume the existing draft recipient is the requested role.
[shr-00075] For tasks that require sending or scheduling a personalized email to each member of a role group (e.g., each friend, each family member), resolve the full group from apis.phone.search_contacts with the requested relationship, then create one draft per person with that person's email and their own computed schedule. Do not combine all recipients into one draft unless the task explicitly asks for a single email to everyone.
[shr-00083] Date-based scheduling current-date source: before computing next birthdays/anniversaries, check apis.supervisor.show_profile live spec for a current_date/current_datetime field; if exposed, use it as the authoritative now, otherwise use datetime.now(); never use JWT expiry, message timestamps, or printed examples.
## APIs TO USE FOR SPECIFIC INFORMATION
[api-00004] You can use the "supervisor" app to get information about my accounts and use the "phone" app to get information about friends and family.

[api-00009] Amazon cart/order schema: apis.amazon.show_cart returns a dict with cart_items (list of product objects with product_id, product_name, quantity, price), not a bare list of IDs. apis.amazon.place_order requires payment_card_id and address_id and orders ALL items currently in the cart.
[api-00014] Amazon payment/address/order schemas: apis.amazon.show_payment_cards returns a list of card objects with payment_card_id, card_name, owner_name, card_number, expiry_year, and expiry_month; apis.amazon.show_addresses returns a list of address objects with address_id, name, street_address, city, state, country, and zip_code; apis.amazon.place_order success returns message and order_id. Retrieve these into variables, choose a non-expired card and valid address, and after placing the order call apis.amazon.show_order using the parameters required by its spec, typically order_id and access_token, to verify the ordered items.
[api-00017] Simple Note search schema: apis.simple_note.search_notes returns note metadata such as note_id, title, and tags, but not the note content. For each candidate note, call apis.simple_note.show_note and store the full content in a variable before parsing or answering.
[api-00019] Amazon show_order schema: apis.amazon.show_order returns order_id, address_id, payment_card_id, paid_amount, and order_items (each with product_id, ordered_quantity, returned_quantity, gift_wrap_quantity, price). Use these fields to assert the order used the selected card/address and ordered exactly the target products.
[api-00025] Phone contact/message schemas: apis.phone.search_contacts returns contact objects with phone_number and relationships; apis.phone.search_text_messages returns message objects with sender.phone_number, message, and sent_at. Use relationships to filter eligible contacts, use phone_number to query each thread, and use sent_at to keep only replies after the inquiry; paginate until empty.
[api-00026] Amazon promo/cart schema: apis.amazon.show_cart returns discount, total_cost, promo_code, and promo_valid in addition to cart_items. apis.amazon.apply_promo_code_to_cart returns a success message but raises a 422 exception for invalid codes or codes whose minimum cart amount is not met. Test candidate codes on the exact target-only cart, catch 422, and select the code with the largest valid discount.
[api-00032] Phone message direction schema: apis.phone.search_text_messages returns both sender and receiver objects with phone_number. To locate an original inquiry sent by the supervisor, filter messages where sender.phone_number equals the supervisor's phone number and receiver.phone_number is in the verified contact set; to collect replies, filter sender.phone_number equals the contact's phone_number. Do not use keyword-only search to find the inquiry or replies.
[api-00036] Amazon order/cart totals and required parameters: apis.amazon.show_cart returns base_cost, tax, delivery_fee, gift_wrap_fee, discount, total_cost, promo_code, promo_valid, and cart_items with gift_wrap_quantity; apis.amazon.show_order returns discount in addition to paid_amount and order_items; apis.amazon.place_order requires payment_card_id, address_id, and access_token. Use these fields to compute expected pre/post-order totals instead of hardcoding values.
[api-00040] Venmo transaction/comment schemas: apis.venmo.login uses username=account email and returns access_token. apis.venmo.show_transactions returns a list of transaction dicts with transaction_id, amount, description, created_at, sender.email, receiver.email; filter direction='received' and user_email=<verified payer email>, then paginate page_index until empty because default page_limit is only 5. apis.venmo.create_transaction_comment requires transaction_id, comment, access_token and returns comment_id/message; verify with apis.venmo.show_transaction_comments, which returns comment objects containing the comment text.
[api-00041] Amazon duplicate/address schemas: apis.amazon.show_orders returns a paginated list of order objects including order_id and order_items with product_id and ordered_quantity; before placing a new purchase, paginate it and check whether target_product_id was already ordered in the needed quantity. apis.amazon.show_addresses includes address objects with name; when the task specifies home/work, select by exact name such as name=='Home' rather than only checking completeness.
[api-00050] Amazon show_orders schema: apis.amazon.show_orders returns order objects with order_id, address_id, payment_card_id, paid_amount, discount, created_at, and order_items list with product_id, ordered_quantity, returned_quantity, gift_wrap_quantity, price, expected_delivery_at, delivered_at. Use ordered_quantity, not returned_quantity, for duplicate checks and product_id from payload.
[api-00051] Amazon Prime subscription payment schema: apis.amazon.show_prime_subscriptions returns paginated subscription objects with prime_subscription_id, start_date, end_date, payment_card_digits, and paid_amount; it does not return payment_card_id. For last Prime membership payment, paginate all pages, select latest_sub = max(prime_subs, key=lambda s: (s['start_date'], s['prime_subscription_id'])), then map latest_sub['payment_card_digits'] to apis.amazon.show_payment_cards by comparing the last four digits of card_number. Do not infer the Prime payment card from show_orders unless Prime subscriptions are unavailable.
[api-00055] Spotify premium subscription/card schemas: apis.spotify.show_premium_subscriptions returns paginated subscription dicts with premium_subscription_id, start_date, end_date, payment_card_digits, paid_amount, and no card_name; apis.spotify.show_payment_cards returns payment_card_id, card_name, owner_name, card_number (numeric/float), expiry_year, expiry_month, cvv_number; apis.supervisor.show_payment_cards takes no parameters and returns owner_name, card_name, card_number, expiry_year, expiry_month, cvv_number but no payment_card_id; apis.spotify.download_premium_subscription_receipt returns message and file_path and can require file_system_access_token; apis.file_system.show_file returns a dict with content.
[api-00060] Amazon/supervisor card registry schemas: apis.amazon.show_payment_cards returns currently saved Amazon cards and may omit deleted cards used for historical Prime subscriptions. apis.supervisor.show_payment_cards is the global card registry and may contain deleted/cross-app cards; use it as fallback only when its live docs/description indicate that scope. apis.supervisor.show_profile returns supervisor profile information; check its live spec for the name field and use it to verify owner_name on fallback cards. Both card lists may return card_number as numeric/float, so use the string-safe last4 helper.
[api-00062] Gmail/file_system attachment and scheduling schemas: apis.file_system.show_directory returns a list of absolute path strings, not file objects; use substring, recursive=True, and entry_type='files' to locate a file. apis.gmail.upload_attachments_to_draft requires draft_id, attachment_file_paths (absolute paths starting with /), file_system_access_token, and gmail access_token, and returns message and attachment_ids. apis.gmail.update_draft scheduled_send_at uses YYYY-MM-DD|HH:MM:SS; apis.gmail.show_draft returns scheduled_send_at in ISO format. Verify a ~/ path with file_exists, then derive the absolute path from the show_directory payload.
[api-00067] Gmail show_drafts schema: apis.gmail.show_drafts returns a paginated list of draft objects with draft_id, subject, body, recipients, attachments, scheduled_send_at, created_at, and updated_at. A query such as 'resignation' can return irrelevant drafts, so paginate page_index until empty, filter by exact subject/body evidence, assert exactly one target draft, and assign draft_id from the filtered payload.
[api-00071] Phone contact email schema: apis.phone.search_contacts returns contact objects with email, phone_number, and relationships. When resolving a role recipient (manager, family, etc.), paginate until empty, assert exactly one matching role, and assign role_email = contacts[0]['email'] from the stored payload; never copy the printed email into later Gmail assertions or update_draft calls.
[api-00072] file_system.file_exists schema: apis.file_system.file_exists returns a dict with an exists boolean. Before deriving an absolute path or uploading an attachment, assert exists_result['exists'] is True; if false, stop and re-check the path rather than proceeding.
[api-00076] Gmail create_draft scheduling schema: apis.gmail.create_draft accepts recipient_email_addresses as a list of strings, subject, body, access_token, and optional scheduled_send_at in YYYY-MM-DD|HH:MM:SS format. It returns message and draft_id. Use create_draft directly when scheduling new personalized emails; do not assume scheduling is only available through update_draft. When verifying with apis.gmail.show_draft, compare scheduled_send_at by normalizing the expected pipe format to ISO, e.g. expected_iso = scheduled_send_at.replace('|', 'T').
[api-00077] Phone contact birthday schema: apis.phone.search_contacts returns contact objects that can include birthday in YYYY-MM-DD format along with email, phone_number, and relationships. For birthday, anniversary, or date-based scheduling tasks, paginate search_contacts until empty for the requested relationship, store full contact objects, and use each contact's email for Gmail recipients and birthday for date computation.
[api-00081] Phone/Gmail login identity schemas: apis.phone.login uses username set to the supervisor's phone_number and password, returning access_token; apis.gmail.login uses username set to the supervisor's email and password, returning access_token. For per-contact scheduled email tasks, store supervisor identifiers and each contact's email/birthday in variables from authoritative payloads or task/profile information, and never hardcode printed example identifiers.

## COMMON MISTAKES AND CORRECT STRATEGIES

[cms-00010] To order a subset from Amazon when place_order orders the whole cart: identify target products programmatically (e.g., via show_product/product type/metadata, not hardcoded IDs), save non-target cart items, delete non-target items, verify cart, place order, then re-add saved items to preserve the user's cart.
[cms-00011] Never use truncated console output as the source of truth. Keep full API payloads in variables; if a parser returns empty, debug by printing repr of sample lines and checking line indentation before manually extracting or hardcoding results.
[cms-00015] When restoring an Amazon cart after a subset order, save and restore all relevant cart attributes, not only product_id and quantity: keep gift_wrap_quantity and reapply gift wrapping with add_gift_wrapping_to_product if it was greater than zero. Also retrieve passwords from apis.supervisor.show_account_passwords into variables and pass those variables to login; do not hardcode printed example passwords or card/address IDs.
[cms-00020] For Amazon payment/address selection, compute payment_card_id and address_id from returned lists; filter cards by expiry_year/expiry_month against a current-date source (not JWT expiry), prefer the latest valid expiry, and select a complete address. Never hardcode IDs after reading them from output.
[cms-00021] Wrap Amazon subset-order cart edits in try/except/finally: after saving non-target items, delete non-targets, verify, place order, and restore saved items in finally if any deletion, verification, or place_order step fails.
[cms-00027] When selecting an Amazon product for purchase, do not trust the first printed search row or hardcode product_id. Paginate apis.amazon.search_products, filter exact product_name and product_type (or confirm with apis.amazon.show_product), and assign target_product_id from the API payload. For promo-code purchases, keep target_product_id, selected_card_id, selected_address_id, and selected_promo_code in variables derived from API responses.
[cms-00028] If a promo code fails because of a minimum cart amount, treat it as inapplicable for a target-only subset order unless the task explicitly allows adding extra qualifying items. Do not silently ignore threshold failures; record the reason and compare only codes valid for the exact cart being ordered.
[cms-00029] Wrap the entire destructive Amazon subset-order workflow—including clear/add, promo-code testing, applying the selected code, place_order, and cart restoration—in try/finally. If any step fails, restore the saved cart items and gift wrapping before surfacing the error.
[cms-00035] Try/finally start point: begin the outer try immediately after saving the original cart and before the first destructive cart mutation (clear_cart, add_product_to_cart with clear_cart_first=True, promo-code testing, applying the selected code). The finally block must restore saved cart items and gift wrapping even if promo testing or code application fails; do not wrap only place_order and restoration.
[cms-00037] Promo-code transaction cleanup: use one outer try after saving the original cart and before the first destructive mutation; keep clear/add, promo testing, applying the selected code, and place_order inside it. In finally, call remove_promo_code_from_cart if any code was applied, then restore saved cart items and gift wrapping. Do not use a nested try for the initial clear/add that re-raises without restoring, and do not restore only after successful place_order.
[cms-00043] For Venmo-funded purchases, never pick the first received transaction or infer the item from the cart alone. Paginate all received transactions from the verified payer, use the transaction description/amount as authoritative provenance, and distinguish payments for the requester from payments for third parties. Do not place a duplicate Amazon order without checking show_orders, and do not require paid_amount to equal the Venmo amount because paid_amount includes tax/delivery while the Venmo amount may only cover product price.
[cms-00044] When saving/restoring an Amazon cart for a subset order, preserve promo_code and promo_valid as well as gift_wrap_quantity. If the original cart had a promo, reapply it after restoration and verify discount/total_cost match the saved original; if a test code was applied, remove it before restoring.
[cms-00047] Never copy literal IDs from console output into later calls, such as product_id=2671 or transaction_id=8234. After filtering API payloads, assign target_product_id, selected_transaction_id, selected_card_id, and selected_address_id to variables, assert they are non-null and match provenance, then use only those variables. If an ID appears only in printed output, re-derive it from the stored API object.
