## STRATEGIES AND HARD RULES
[shr-00001] Make sure to end code blocks with ``` followed by a newline(\n).
[shr-00005] Always look at API specifications (using apis.api_docs.show_api_doc) before calling an API.
[shr-00006] Write small chunks of code and only one chunk of code in every step. Make sure everything is working correctly before making any irreversible change.

[shr-00056] For irreversible money-moving actions, require programmatic gates before execution: authoritative note parsed, exact recipient email resolved, balance checked, and post-mutation state verified. Do not proceed if any identity or amount is ambiguous.
[shr-00058] Before irreversible Venmo payments/requests, run an idempotency gate: paginate sent transactions and sent payment requests, filter by the exact current-task description (e.g., 'For Athens trip') plus receiver email and amount, and skip or report already-existing entries. Do not create duplicates merely because the note still lists the debt.
[shr-00072] API documentation gate: apis.api_docs.show_api_descriptions is not a substitute for apis.api_docs.show_api_doc. Before the first call to every API in the current environment—including supervisor.show_account_passwords and supervisor.complete_task—fetch its doc, assert required parameters and response schema, and only then call it. Do not infer schemas from printed descriptions or prior tasks.
[shr-00084] For Venmo/phone money-moving pagination loops (phone.search_contacts, venmo.search_users, venmo.show_received_payment_requests, venmo.show_transactions), a non-list response is a failure dict and must abort immediately. Assert isinstance(page, list) and stop/raise on failure; do not break and continue with partial data, because incomplete identity or amount data can cause irreversible wrong payments.
[shr-00087] When an API doc lists parameter constraints (e.g., page_limit <= 20), extract and enforce them before the first call; for paginated list endpoints, use a compliant page_limit (often 20) and assert isinstance(page, list), aborting on failure dicts rather than continuing with partial data.
[shr-00095] For conditional money actions such as 'withdraw the remaining balance, if any', branch on the authoritative post-approval balance: if balance > 0 perform the withdrawal and verify it; if balance == 0 skip the withdrawal and do not assert amount > 0. Never force an irreversible mutation when the task permits a no-op.
[shr-00096] For batch Venmo approvals/denials, verification must be state-complete: after mutation, assert target IDs are absent from the prior status AND present in the new status; reconcile balance programmatically as initial_balance - sum(approved_amounts) == post_balance before any withdrawal.
[shr-00105] For batch Venmo approvals/denials, add a pre-mutation freshness gate: immediately before the approval loop, re-fetch status='pending', deduplicate by payment_request_id, and assert each target ID is still pending, current-month, and receiver email equals supervisor email. Do not approve from a stale snapshot; this prevents duplicate or stale irreversible approvals.
[shr-00106] Enforce the API documentation gate programmatically: maintain a fetched_docs set in the current environment; before every API call, assert (app_name, api_name) in fetched_docs, and if absent call apis.api_docs.show_api_doc(app_name=..., api_name=...) and add it. Apply this to all APIs, including supervisor.complete_task, rather than relying on prior tasks or printed descriptions.
[shr-00107] For Venmo sends, treat insufficient venmo_balance as a funding branch, not a fatal ambiguity. If balance >= amount, call create_transaction without payment_card_id. If balance < amount, first search supervisor and venmo account/profile API docs for default/primary payment-card endpoints and use an authoritative default if present. Otherwise call venmo.show_payment_cards, filter owner_name matching the supervisor and non-expired cards using datetime.now(); if exactly one valid card remains, use its payment_card_id. Only report ambiguity if multiple valid cards remain and no authoritative default exists.
[shr-00112] For direct Venmo sends, enforce gate order: identity resolution -> sent-transaction idempotency -> funding-source resolution -> mutation -> verification. Never call supervisor.complete_task(status='fail') for funding ambiguity until the idempotency gate has been run; if a matching sent transaction already exists, complete the task as success without creating a duplicate.

[api-00009] Spotify queue APIs: apis.spotify.show_song_queue returns a list of song objects with fields such as song_id, title, position, is_playing, and is_current. apis.spotify.remove_song_from_queue takes an integer position parameter (documented as 0-indexed). apis.spotify.play_music(access_token=...) with no optional parameters plays the current queue song and returns a success object like {"message": "...", "song_id": ...}.
[api-00013] Spotify liked/playback return schemas: apis.spotify.show_liked_songs returns a page of liked song objects containing song_id, so build liked_song_ids by paginating until an empty or short page. apis.spotify.remove_song_from_queue returns a success message object, and apis.spotify.show_current_song returns an object including song_id and is_playing; use these fields to validate mutations and playback state.
[api-00020] Spotify playlist schemas differ: apis.spotify.show_playlist_library returns a list of playlist summaries containing song_ids, which is a list of integer song IDs. apis.spotify.show_playlist returns playlist detail containing songs, which is a list of song objects with fields such as id, title, and artist_ids, not song_ids. When verifying a specific playlist's contents, use set(s['id'] for s in detail['songs']). When verifying that songs were removed from source playlists, you can use the library summaries' song_ids or the detail endpoint's songs IDs, but always use the field defined by the endpoint you actually called.
[api-00025] Spotify create_playlist and ownership schemas: apis.spotify.create_playlist returns a success object containing message and playlist_id; failure also contains message, so assert 'created' in message.lower() and that playlist_id is an integer. apis.spotify.show_playlist_library summaries include owner.email; when a task says 'my playlists', filter by the supervisor's email before mutating, because the library may include non-owned playlists.
[api-00028] Spotify song detail and file-system schemas for file-to-playlist matching: apis.spotify.show_song(song_id=...) returns a dict with title and artists, where artists is a list of objects containing id and name; use it to resolve artist names because playlist detail only exposes artist_ids. apis.file_system.show_file(file_path='~/...', access_token=...) returns a dict with content (string); parse the content lines. apis.spotify.search_playlists returns a page of playlist summaries with title, owner.email, and song_ids, and the query is fuzzy, so filter exact titles and paginate.

If both query and sort_by are given, relevance ranking can interfere with global date order, so collect all pages and sort/filter by parsed title date. apis.simple_note.show_note returns a dict with content string. apis.simple_note.create_note returns a dict with message and note_id on success, but failure can also contain message; assert a semantic marker such as 'created' in message.lower() and integer note_id. apis.simple_note.update_note can modify title/content/tags/pinned if a note for the target date already exists.
[api-00039] Simple Note update_note response schema: apis.simple_note.update_note returns a dict with message and note_id on success, but failure can also contain message; assert a semantic marker such as 'updated' in message.lower() and integer note_id before using the note_id or calling show_note.

Prefer apis.simple_note.search_notes(tags=['habit-tracker'], dont_reorder_pinned=True) and paginate all pages; if using query, do not assume exact title matching—filter by tag and regex date extraction.

## COMMON MISTAKES AND CORRECT STRATEGIES

[cms-00010] For queue mutation tasks, do not rely on visual inspection of printed output to count items. Compute target positions/IDs programmatically, e.g. liked_positions = [song['position'] for song in queue if song['song_id'] in liked_song_ids], and print/assert len(liked_positions). When removing multiple items by position, either delete from highest position to lowest from a snapshot or re-fetch the queue after each deletion to avoid position-shift bugs.
[cms-00014] For queue mutations, do not ignore API return values or stale position fields. Capture each remove_song_from_queue result and assert it indicates success. Before using a queue snapshot's position field, verify that song['position'] matches the enumerate(queue) index; if it does not, use enumerate-derived 0-indexed positions or re-fetch after each deletion.
[cms-00017] For remove_song_from_queue, do not treat a response dict containing 'message' as proof of success because failure responses also contain a message. Assert a semantic success marker such as 'Removed' in res['message'] (optionally also checking the expected position), then re-fetch the queue to confirm the target song is absent.
[cms-00021] For playlist mutation tasks, do not infer a detail API schema from a list API. In particular, do not validate apis.spotify.show_playlist output by reading song_ids; that field belongs to apis.spotify.show_playlist_library. For remove_song_from_playlist and add_song_to_playlist, capture each response and assert a semantic success marker such as 'removed' or 'added' in the message, then re-fetch using the correct endpoint-specific schema. Treating any dict with a message as success is insufficient because failure responses can also contain a message.
[cms-00024] For structured text parsing (notes, files, or other line-based content), do not rely on exact leading spaces after line.strip(); use whitespace-insensitive checks or regex, e.g. line.lstrip().startswith('-') and 'director:' in line. Assert that parsed counts are non-empty and match expected counts, and assert that all intended entries matched. Never replace a failed parser with hardcoded values from visual inspection; debug the parser or report the mismatch.
[cms-00027] When selecting a maximum by like_count or a similar metric, detect ties by collecting all items with the maximum value and either return all tied titles or explicitly state the tie; do not silently pick the first encountered item.
[cms-00029] For file-to-playlist archive matching, do not compare raw strings only. Normalize titles and artist names (lowercase, strip, collapse whitespace) before exact artist-set equality. Assert every file entry has exactly one matched song or explicitly handle multiple candidates; assert unmatched_entries is empty and len(matched_songs) == len(file_entries).
[cms-00030] For duplicate playlist title checks, do not treat one search_playlists page as exhaustive. Paginate search_playlists until a short or empty page, collect all exact title matches, and also check the complete owned playlist library before create_playlist.
[cms-00031] For playlist removals, do not loop over stale occurrence counts assuming each remove_song_from_playlist call deletes exactly one occurrence. Re-fetch the playlist after removals and continue while the target song_id remains, or remove once and verify the count is zero; handle already-removed cases idempotently.
[cms-00036] For date-relative note tasks, do not infer 'today' or 'yesterday' from updated_at of existing notes, created_at of first result, or default search order. Derive today from an authoritative current-date source (datetime.now().date().isoformat() if available; otherwise create a temporary note and use its returned created_at date, then update title if needed). Paginate all matching notes, parse the date from the title (e.g. 'Habit Tracking Log for YYYY-MM-DD'), and select the note whose parsed date is exactly yesterday; assert the selected date equals yesterday. Before creating, search for an existing note for today and update it instead of duplicating unless the task explicitly requires a new note.
[cms-00040] For habit-log copy tasks, do not assume the target line must change from yesterday's value. Treat the edit as idempotent state-setting: locate the target habit line, e.g. practiced_meditation, and set it to the requested value, e.g. no, regardless of whether it was already no; assert the target line exists and all non-target lines are unchanged, allowing zero changed lines when yesterday already had the desired state.
[cms-00043] For date-based note duplication, never hardcode yesterday_note_id from printed output. After collecting all pages, group notes by parsed title date, assert exactly one note has parsed date == yesterday (and expected habit-tracker tag), assert zero notes have parsed date == today before create_note, then use yesterday_notes[0]['note_id'] programmatically before show_note/create_note.
[cms-00044] For pagination loops, do not run a second 'while True' search after the first loop has advanced page_index to an empty or short page unless you reset page_index=0; otherwise the second loop stops immediately and falsely proves completeness. Either collect all pages in one loop or reset page_index before re-searching.
[cms-00052] For financial tasks, do not visually pick recipients from fuzzy contact search output or hardcode emails. Paginate/filter phone.search_contacts, require exact first_name (and last_name if known), assert relationships contains the expected relationship such as 'friend', assert exactly one candidate, and extract email from the response. If multiple candidates or no friend match, confirm via venmo.search_users/search_friends or stop and report ambiguity before moving money.
[cms-00053] For expense-note settlement, do not rely on fuzzy search_notes query results. Paginate all pages, filter exact title (e.g., 'Maui trip'), assert exactly one note, then show_note. Parse every non-header line with explicit regex/rules; assert each line matches exactly one direction ('I owe X => $Y' or 'X owes me => $Y'), amounts are positive, and all expected names/entries are present. Never hardcode amounts/names from printed output.
[cms-00057] For Venmo money-moving tasks, separate relationship proof from payment-account proof: Phone contacts are authoritative for 'friend' relationships; Venmo only needs to confirm the resolved email is a valid Venmo account via search_users or show_profile. Do not require search_friends or assert all recipients are Venmo friends unless the task explicitly says Venmo friends; if search_friends misses a valid user, proceed after search_users confirms the account.
[cms-00060] When a task specifies an exact reply payload format (e.g., 'list of comma-separated movie titles'), send only that format in the message body; do not add explanatory prose such as 'Here are...'. If parsing fails, debug the parser or report the mismatch; never hardcode values from visual inspection.

Paginate all search_notes pages, filter candidates by expected tags (e.g., health) and exact/normalized title (e.g., Weekly Exercise Plan), assert exactly one candidate, then show_note and assert the returned title matches before parsing content.

[cms-00077] For Venmo reject-and-send corrected-amount tasks, never hardcode printed payment_request_id, sender.email, or corrected_amount after computing them. Store target_request = candidates[0], recipient_email = target_request['sender']['email'], corrected_amount = round(target_request['amount'] * 1.05, 2), and pass those variables to deny_payment_request/create_transaction. Derive current date from datetime.now() or another authoritative environment timestamp, filter by exact description, receiver email, sender email/relationship, and current month/year, assert exactly one candidate; if multiple or zero, disambiguate by amount/relationship or stop rather than selecting visually.

A decrease/discount uses factor = 1 - pct (e.g., 10% decrease => round(original_amount * 0.9, 2)) and assert corrected_amount < original_amount; an increase uses factor = 1 + pct and assert corrected_amount > original_amount. [cms-00091] For tasks asking which genre of songs I have liked least/most in my Spotify album library, do not treat show_album_library as the source of liked songs. The word 'liked' makes apis.spotify.show_liked_songs authoritative; use show_album_library only to define the album-library scope by collecting its song_ids and intersecting with liked_song_ids before genre aggregation. If the task explicitly asks all songs in the album library without 'liked', then album-library song_ids may be used, but justify that interpretation. Compute min for least and max for most, collect all tied genres, return them comma-separated, and handle empty liked/album intersections explicitly.

Implement an explicit branch: if post_balance > 0.01, call withdraw_from_venmo_balance with amount=post_balance and verify the transfer; else skip withdrawal, assert post_balance <= 0.01, and verify no new venmo_to_card transfer was created.
