## STRATEGIES AND HARD RULES
[shr-00001] Make sure to end code blocks with ``` followed by a newline(\n).
[shr-00005] Always look at API specifications (using apis.api_docs.show_api_doc) before calling an API.
[shr-00006] Write small chunks of code and only one chunk of code in every step. Make sure everything is working correctly before making any irreversible change.

[shr-00056] For irreversible money-moving actions, require programmatic gates before execution: authoritative note parsed, exact recipient email resolved, balance checked, and post-mutation state verified. Do not proceed if any identity or amount is ambiguous.
[shr-00058] Before irreversible Venmo payments/requests, run an idempotency gate: paginate sent transactions and sent payment requests, filter by the exact current-task description (e.g., 'For Athens trip') plus receiver email and amount, and skip or report already-existing entries. Do not create duplicates merely because the note still lists the debt.
[shr-00072] API documentation gate: apis.api_docs.show_api_descriptions is not a substitute for apis.api_docs.show_api_doc. Before the first call to every API in the current environment—including supervisor.show_account_passwords and supervisor.complete_task—fetch its doc, assert required parameters and response schema, and only then call it. Do not infer schemas from printed descriptions or prior tasks.
[shr-00084] For Venmo/phone money-moving pagination loops (phone.search_contacts, venmo.search_users, venmo.show_received_payment_requests, venmo.show_transactions), a non-list response is a failure dict and must abort immediately. Assert isinstance(page, list) and stop/raise on failure; do not break and continue with partial data, because incomplete identity or amount data can cause irreversible wrong payments.
[shr-00087] When an API doc lists parameter constraints (e.g., page_limit <= 20), extract and enforce them before the first call; for paginated list endpoints, use a compliant page_limit (often 20) and assert isinstance(page, list), aborting on failure dicts rather than continuing with partial data.
[shr-00095] For conditional money actions such as 'withdraw the remaining balance, if any', branch on the authoritative post-approval balance: if balance > 0 perform the withdrawal and verify it; if balance == 0 skip the withdrawal and do not assert amount > 0. Never force an irreversible mutation when the task permits a no-op.
[shr-00096] For batch Venmo approvals/denials, verification must be state-complete: after mutation, assert target IDs are absent from the prior status AND present in the new status; reconcile balance programmatically as initial_balance - sum(approved_amounts) == post_balance before any withdrawal.
[shr-00105] For batch Venmo approvals/denials, add a pre-mutation freshness gate: immediately before the approval loop, re-fetch status='pending', deduplicate by payment_request_id, and assert each target ID is still pending, current-month, and receiver email equals supervisor email. Do not approve from a stale snapshot; this prevents duplicate or stale irreversible approvals.
[shr-00106] Enforce the API documentation gate programmatically: maintain a fetched_docs set in the current environment; before every API call, assert (app_name, api_name) in fetched_docs, and if absent call apis.api_docs.show_api_doc(app_name=..., api_name=...) and add it. Apply this to all APIs, including supervisor.complete_task, rather than relying on prior tasks or printed descriptions.
[shr-00107] For Venmo sends, treat insufficient venmo_balance as a funding branch, not a fatal ambiguity. If balance >= amount, call create_transaction without payment_card_id. If balance < amount, first search supervisor and venmo account/profile API docs for default/primary payment-card endpoints and use an authoritative default if present. Otherwise call venmo.show_payment_cards, filter owner_name matching the supervisor and non-expired cards using datetime.now(); if exactly one valid card remains, use its payment_card_id. Only report ambiguity if multiple valid cards remain and no authoritative default exists.
[shr-00112] For direct Venmo sends, enforce gate order: identity resolution -> sent-transaction idempotency -> funding-source resolution -> mutation -> verification. Never call supervisor.complete_task(status='fail') for funding ambiguity until the idempotency gate has been run; if a matching sent transaction already exists, complete the task as success without creating a duplicate.
[shr-00117] For Venmo payment-request tasks, use request-specific gates: resolve exact friend email via phone contacts, confirm the email is a valid Venmo account, run sent-request idempotency over all pages, create only if no exact match, then verify post-mutation state. Do not require Venmo balance or funding-card resolution because requests do not immediately move money. If an exact matching sent request already exists, verify it and complete as success rather than creating a duplicate or failing.
[shr-00122] For relationship-specific Venmo requests/payments, resolve the recipient with phone.search_contacts using the exact relationship parameter when supported (e.g., relationship='roommate'), filter exact first/last name, and assert exactly one candidate. If the relationship-filtered search returns zero candidates, do not fallback to any single name-only match; stop/fail before Venmo confirmation or mutation.
[shr-00123] Venmo payment-request idempotency must be lifecycle-aware: fetch the doc for show_sent_payment_requests and, when status or lifecycle fields are available, count only active/pending requests as duplicates. Denied or cancelled matching requests do not satisfy the current ask and must not suppress creation; approved requests should be verified against task intent before deciding whether a new request is needed.
[shr-00126] For Venmo payment requests, make idempotency and verification lifecycle-aware, privacy-aware, and sender-email-aware: resolve the authenticated Venmo account email via apis.venmo.show_profile and use it as the authoritative sender.email; match existing duplicates only when the request is active/pending (or approved_at/denied_at are null when status filtering is unavailable), the exact description/amount/receiver email match, and private matches the requested state (private=False for public asks). Denied, cancelled, approved, or private-mismatched requests are not valid duplicates for a new public pending ask and must not suppress creation.
[shr-00128] For irreversible file-system mutations, use a programmatic gate: parse the original file, build new content from original rows, assert header/row count/non-target columns unchanged, call update_file, then re-read and verify the full file. Do not assume standard modules are available; io is disallowed, so parse CSV manually with splitlines/split instead of csv.reader(io.StringIO(...)).
[shr-00129] For event RSVP/state-sync tasks, derive the invitation cutoff from the actual invitation sent to each invitee: prefer an exact invitation template or the earliest supervisor message to that contact after the tracking file was created. Do not use the latest message containing a keyword such as 'reunion', because reminders or unrelated mentions can move the cutoff past real replies.
[shr-00130] When classifying replies for RSVPs, classify every post-invitation reply, ignore unrelated/unclassified messages, take the latest classified reply, and leave the field unknown if no classified reply exists. Do not require the latest raw message to match a marker or assert exactly one category for every raw reply.
[shr-00138] For CSV/file-system state-sync tasks, enforce response-contract gates: after login assert isinstance(login_result, dict) and 'access_token' in login_result; after show_file assert isinstance(file_info, dict), 'content' in file_info, and 'created_at' in file_info; after update_file assert result.get('message') == 'File content updated.' and result.get('file_path') == target_path, not substring 'updated'; then re-read and compare normalized content exactly.
[shr-00139] For RSVP invitation cutoff, implement fallback: if no exact invitation template is found, use earliest supervisor message with sent_at >= file_info['created_at']; assert cutoff >= file_info['created_at']. Do not silently proceed when cutoff is missing or before file creation.
[shr-00143] For file-system export tasks, make the write idempotent: call apis.file_system.file_exists and assert isinstance(res, dict) and 'exists' in res. If exists is true, use update_file; if false, ensure the parent directory exists (directory_exists/create_directory if needed) and then create_file. Assert exact documented success markers ('File content updated.' or 'File created.') and a non-empty file_path that resolves to the target path; create_file may return an absolute path, so compare normalized path or suffix rather than literal '~/...'. Re-read and compare normalized content.
[shr-00149] For file-system export tasks, checking directory_exists is not sufficient when the parent directory is missing: call create_directory and assert its exact documented success marker before calling create_file. Do not assume directory creation succeeded merely because the subsequent create_file call appears to work.
[shr-00151] For multi-app export tasks, gate every login used to read source and write destination: after simple_note.login and file_system.login assert isinstance(login_result, dict) and 'access_token' in login_result before using tokens. A printed token-like string is not enough; failure dicts must abort.
[shr-00153] For broadcast irreversible messaging to all contacts with a relationship (e.g., all roommates), do not reuse single-recipient exact-one gates. Derive recipients from apis.phone.search_contacts with the relationship filter, paginate until an empty page, deduplicate by contact_id and phone_number, assert each has non-empty phone_number and expected relationship, assert len(recipients)>0 unless the task permits zero, and assert len(successful_results)==len(recipients). Never hardcode observed recipient counts.
[shr-00154] For each irreversible voice/text send in a broadcast, gate the mutation immediately: call apis.phone.send_voice_message or apis.phone.send_text_message, assert the exact documented success marker and integer message ID before proceeding to the next recipient; stop/raise on failure. Optionally verify persisted state with apis.phone.search_voice_messages or apis.phone.search_text_messages filtered by the resolved phone_number and exact message.
[shr-00159] For single-recipient relationship messaging (e.g., 'my partner'), resolve the recipient with apis.phone.search_contacts using the relationship filter, paginate all pages, deduplicate by contact_id and phone_number, assert the chosen contact's relationships contains the requested relationship, and assert a non-empty phone_number. If zero or multiple unique recipients remain, call apis.supervisor.complete_task(status='fail') without answer before any send; do not rely on a bare assert to abort an ambiguous irreversible action.
[shr-00165] For period-keyed note logs (e.g., monthly expense entries), make idempotency key-level, not exact-string: derive the current period key from datetime.now(), parse existing rows, and if a row for that period already exists replace it with the computed value or skip if identical; if absent insert it in the note's existing sort order. Assert exactly one row per period before mutation. Do not append a duplicate month merely because the exact new line was not found.
[shr-00166] When aggregating date-filtered API data, treat server-side date boundaries as ambiguous unless documented: paginate all pages, deduplicate by the entity ID (e.g., transaction_id), and client-side filter by the authoritative period (e.g., created_at.startswith('YYYY-MM') or parsed date month/year). Do not rely solely on min_created_at/max_created_at, because inclusive/midnight semantics can miss or include boundary records.
[shr-00170] For irreversible SimpleNote note mutations (e.g., updating a monthly expense log), resolve the target note_id programmatically before update_note: paginate all search_notes pages (using query/tags/no-query as needed), filter exact normalized title (strip/lower/collapse whitespace), assert exactly one candidate, then show_note and assert the returned title and content before mutation. Never hardcode note_id from printed fuzzy search output.
[shr-00171] Credential hygiene for supervisor.show_account_passwords: never print or log the full returned password list. Extract only the required account_name into a variable, e.g. simple_note_password = next(item['password'] for item in passwords if item['account_name'] == 'simple_note'), and print only non-sensitive identifiers or masked values if debugging is needed.
[shr-00176] For Venmo received-request aggregation, enforce a closed time window and identity/status gates: derive now/today from datetime.now(); for 'last N days including today' filter cutoff_date <= created_date <= today (or created_at <= now), not only created_date >= cutoff, so future-dated records cannot be included. Resolve the authenticated Venmo receiver email via apis.venmo.show_profile or proven login/profile data and assert each counted request has receiver.email equal to it. Decide status semantics explicitly: event-based 'have been requested' totals include pending, approved, and denied requests unless the task asks outstanding/pending/active, in which case filter status='pending' or treat approved_at/denied_at null as active when status filtering is unavailable. Assert supervisor.show_account_passwords returns a list and never print the extracted password variable; print only account_name or masked length if debugging.
[shr-00179] For read-only Venmo received-request totals, resolve the authenticated receiver email with a fallback ladder when apis.venmo.show_profile fails: (1) inspect venmo.login result for an email field; (2) fetch docs and try venmo.show_account/supervisor.show_profile; (3) if still unavailable, derive venmo_account_email from the authenticated received-request list by collecting distinct receiver.email values, assert exactly one, assign it to a variable, and filter every counted request by that variable. Never hardcode the supervisor personal email or use a dead conditional assert to bypass identity resolution.
[shr-00183] For Splitwise↔Venmo reconciliation, do not match by receiver email + amount alone. Require exact debtor share amount, exact expense payer email as Venmo receiver, authenticated supervisor email as Venmo sender, and a description tie (normalized Venmo description contains the Splitwise expense description or an explicit 'For splitwise => <description>' pattern). Enforce one-to-one uniqueness: each expense has exactly one candidate transaction and each transaction has exactly one candidate expense; otherwise stop before recording.

## APIs TO USE FOR SPECIFIC INFORMATION
[api-00004] You can use the "supervisor" app to get information about my accounts and use the "phone" app to get information about friends and family.

[api-00009] Spotify queue APIs: apis.spotify.show_song_queue returns a list of song objects with fields such as song_id, title, position, is_playing, and is_current. apis.spotify.remove_song_from_queue takes an integer position parameter (documented as 0-indexed). apis.spotify.play_music(access_token=...) with no optional parameters plays the current queue song and returns a success object like {"message": "...", "song_id": ...}.
[api-00013] Spotify liked/playback return schemas: apis.spotify.show_liked_songs returns a page of liked song objects containing song_id, so build liked_song_ids by paginating until an empty or short page. apis.spotify.remove_song_from_queue returns a success message object, and apis.spotify.show_current_song returns an object including song_id and is_playing; use these fields to validate mutations and playback state.
[api-00020] Spotify playlist schemas differ: apis.spotify.show_playlist_library returns a list of playlist summaries containing song_ids, which is a list of integer song IDs. apis.spotify.show_playlist returns playlist detail containing songs, which is a list of song objects with fields such as id, title, and artist_ids, not song_ids. When verifying a specific playlist's contents, use set(s['id'] for s in detail['songs']). When verifying that songs were removed from source playlists, you can use the library summaries' song_ids or the detail endpoint's songs IDs, but always use the field defined by the endpoint you actually called.
[api-00025] Spotify create_playlist and ownership schemas: apis.spotify.create_playlist returns a success object containing message and playlist_id; failure also contains message, so assert 'created' in message.lower() and that playlist_id is an integer. apis.spotify.show_playlist_library summaries include owner.email; when a task says 'my playlists', filter by the supervisor's email before mutating, because the library may include non-owned playlists.
[api-00028] Spotify song detail and file-system schemas for file-to-playlist matching: apis.spotify.show_song(song_id=...) returns a dict with title and artists, where artists is a list of objects containing id and name; use it to resolve artist names because playlist detail only exposes artist_ids. apis.file_system.show_file(file_path='~/...', access_token=...) returns a dict with content (string); parse the content lines. apis.spotify.search_playlists returns a page of playlist summaries with title, owner.email, and song_ids, and the query is fuzzy, so filter exact titles and paginate.
[api-00035] Simple Note note APIs: apis.simple_note.search_notes returns a page/list of note summaries with note_id, title, tags, created_at, updated_at, and pinned, not content. It supports query, tags, pinned, dont_reorder_pinned, sort_by, page_index, and page_limit; default page_limit is small and pinned notes are reordered first. If both query and sort_by are given, relevance ranking can interfere with global date order, so collect all pages and sort/filter by parsed title date. apis.simple_note.show_note returns a dict with content string. apis.simple_note.create_note returns a dict with message and note_id on success, but failure can also contain message; assert a semantic marker such as 'created' in message.lower() and integer note_id. apis.simple_note.update_note can modify title/content/tags/pinned if a note for the target date already exists.
[api-00039] Simple Note update_note response schema: apis.simple_note.update_note returns a dict with message and note_id on success, but failure can also contain message; assert a semantic marker such as 'updated' in message.lower() and integer note_id before using the note_id or calling show_note.
[api-00042] Simple Note habit-log discovery: habit-log titles may be 'Habit Log -- YYYY-MM-DD' rather than 'Habit Tracking Log for YYYY-MM-DD'. Prefer apis.simple_note.search_notes(tags=['habit-tracker'], dont_reorder_pinned=True) and paginate all pages; if using query, do not assume exact title matching—filter by tag and regex date extraction.
[api-00045] Supervisor credentials and Spotify login schemas: apis.supervisor.show_account_passwords returns a list of objects with account_name and password; select the item where account_name == 'spotify'. apis.spotify.login(username=..., password=...) returns an access_token, which should be saved and reused for subsequent Spotify API calls.
[api-00046] Spotify followed-artist schema: apis.spotify.show_following_artists returns a page/list of artist objects containing artist_id, name, genre, follower_count, created_at, and followed_at, not just IDs. For 'most followed artist I follow' tasks, use follower_count directly as the authoritative metric and paginate until an empty or short page.
[api-00048] Spotify followed-artist extremum tasks: apis.spotify.show_following_artists returns artist objects with name and follower_count. For 'least followed' tasks, compute min(follower_count); for 'most followed' tasks, compute max(follower_count). Paginate all pages and collect all tied names. Do not assume followed-artist tasks are always maximum-based.
[api-00051] Venmo and phone contact schemas for money-moving tasks: apis.phone.search_contacts returns a list of contact objects with first_name, last_name, email, phone_number, and relationships; the query is fuzzy and can match address fields, so filter exact first_name/last_name and relationship programmatically. apis.venmo.create_transaction returns a dict with message and transaction_id; success message is 'Sent money.'. apis.venmo.create_payment_request returns a dict with message and payment_request_id; success message is 'Payment request created.'. apis.venmo.show_sent_payment_requests returns a list of request objects containing payment_request_id, amount, description, private, sender, and receiver. Use apis.venmo.search_users or apis.venmo.search_friends to confirm a resolved email is a Venmo account/friend before irreversible payments.
[api-00059] Venmo mutation and idempotency schemas: apis.venmo.create_transaction uses receiver_email, amount, access_token, description, private and returns transaction_id; apis.venmo.create_payment_request uses user_email, amount, access_token, description, private and returns payment_request_id. apis.venmo.show_transactions returns transaction objects with transaction_id, amount, description, private, sender.email, receiver.email and supports direction='sent', user_email, query, page_index, page_limit; use it to detect existing sent payments. apis.venmo.show_sent_payment_requests returns request objects with payment_request_id, amount, description, private, sender.email, receiver.email; use it to detect existing requests.
[api-00061] Phone text-message schemas: apis.phone.search_text_messages returns a page/list of message objects with text_message_id, sender.name, sender.phone_number, message, and sent_at; paginate and filter by the resolved contact phone_number. apis.phone.send_text_message returns a dict with message and text_message_id; success message is 'Text message sent.', so assert that marker and integer text_message_id before treating the reply as sent.
[api-00062] Venmo balance and account-confirmation schemas: apis.venmo.show_venmo_balance returns a dict with venmo_balance (number) on success and message on failure; use it before payments. apis.venmo.search_users returns a page/list of user objects with first_name, last_name, email, registered_at, and friends_since; filter exact email to confirm a phone-resolved email is a valid Venmo account.
[api-00063] Spotify show_song like_count schema: apis.spotify.show_song(song_id=...) returns a dict containing song_id, title, like_count, and artists; use like_count as the authoritative metric for most-liked-song tasks, and do not assume playlist detail contains like_count.
[api-00073] Simple Note search/show failure schemas: apis.simple_note.search_notes success is a list/page of note summaries; failure is a dict containing message. apis.simple_note.show_note success is a dict containing note_id, title, content (string), tags; failure is a dict containing message. Before iterating search results or reading content, assert isinstance(page, list) and isinstance(note, dict) and 'content' in note; if a failure dict appears, stop and debug rather than treating it as empty data.
[api-00076] Venmo received-request and denial schemas: apis.venmo.show_received_payment_requests supports status='pending'/'denied' and pagination; success is a list/page of request objects with payment_request_id, amount, description, created_at, updated_at, approved_at, denied_at, private, sender.email, receiver.email; failure is a dict with message. apis.venmo.deny_payment_request returns a dict with message; success marker is 'Payment request denied.', so assert that marker and re-fetch status='denied' to verify.
[api-00082] Venmo create_transaction privacy schema: apis.venmo.create_transaction accepts optional private with default false; omit private unless the task explicitly requests privacy, and verify the resulting transaction's private field matches the requested/default behavior.
[api-00083] Spotify playlist library schema: apis.spotify.show_playlist_library returns playlist summaries containing playlist_id, owner.email, and song_ids; use playlist_id to call apis.spotify.show_playlist, and filter owner.email == supervisor email for 'my playlists' tasks.
[api-00088] Spotify liked-genre schemas: apis.spotify.show_liked_songs accepts access_token, page_index, page_limit (default 5, max 20), and sort_by; success is a list of liked-song objects with song_id, title, album_id, album_title, duration, artists, and liked_at, but no genre; failure is a dict with message. apis.spotify.show_song(song_id=...) requires only song_id (not access_token unless the doc says otherwise) and returns genre as a string field; use it directly for genre aggregation rather than resolving artists through extra APIs.
