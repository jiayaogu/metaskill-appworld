## STRATEGIES AND HARD RULES
[shr-00001] Make sure to end code blocks with ``` followed by a newline(\n).
[shr-00005] Always look at API specifications (using apis.api_docs.show_api_doc) before calling an API.
[shr-00006] Write small chunks of code and only one chunk of code in every step. Make sure everything is working correctly before making any irreversible change.

[shr-00009] In a new task or environment, re-check the API specification for every API before its first call, even if the same API was used in a previous task. Do not rely on memory for parameter names, required fields, or response schemas.
[shr-00023] Resolve relative dates from an authoritative source. For tasks involving 'today', 'yesterday', 'this week', etc., first obtain the current date from the environment's authoritative source, such as apis.supervisor.show_profile or a documented current-date API; if no such API exists, use the execution environment's system date. Then compare only the date portion of timestamps. Never infer 'today' from the maximum created_at or sent_at timestamp in the dataset, because the latest record may be older than the current date and can cause incorrect filtering.
[shr-00032] When current API documentation conflicts with playbook examples or older snippets, treat the current show_api_doc response schema as authoritative. Do not force data to match an old playbook assumption; adapt the workflow to the documented fields in the active environment.
[shr-00056] When resolving current date from apis.supervisor.show_profile, inspect the API spec and use only documented date/current-date fields. If no documented date field exists, fall back to the execution environment's system date. Do not recursively scan response keys for substrings such as 'current', 'today', 'system', or 'now'.
[shr-00064] For total-from-files tasks, define candidates by semantic category and period, not by file extension. Enumerate all matching files, attempt extraction from each, deduplicate by bill period such as YYYY-MM, prefer readable sources, and explicitly surface unreadable, missing, or conflicting records instead of assuming they contribute zero.
[shr-00068] For total-from-files, derive expected_periods from all candidate filenames for the requested category/year, not only from successfully parsed files. Require exactly one readable amount per expected period. If any expected period has no readable amount because all sources are missing or unreadable, the aggregate is incomplete: do not submit a bare success numeric total. Call complete_task(status='fail', answer='...') or, only if the task explicitly accepts a readable-only total, return a string that names the readable periods and the unreadable/missing period.
[shr-00075] Before any irreversible bulk deletion, complete a read-only validation pass: enumerate all pages, fetch every required detail, normalize IDs, and assert that every in-scope record has a validated response. If any pagination or detail fetch fails, abort/fail before deleting; never delete a partial candidate set.
[shr-00087] For irreversible bulk additions or new-playlist creation, perform a read-only validation pass before writing: paginate all source lists, deduplicate candidate song IDs, fetch every required detail, assert fetch_failures == [] and len(validated)==len(unique_candidate_ids), and only then create/add. For 'this year' filters, use the authoritative current year and compare parsed release_date.year == current_year, not rolling 365 days or unverified string slicing.
[shr-00091] For inclusive multi-year release-date filters such as 'this or last year', derive current_year from the authoritative date and last_year=current_year-1, then compare parsed release_date.year in {current_year, last_year}. Do not use rolling 365 days or string slicing. Print boundary records, such as Dec 31 last_year and Jan 1 current_year, to confirm inclusion/exclusion before irreversible writes.
[shr-00096] For relative-date tasks, after inspecting apis.supervisor.show_profile spec, actually call show_profile to confirm whether a documented current-date field exists. Use that field if present; only after the call shows no documented date field may you fall back to the execution environment's system date. Record the date source used.
[shr-00105] For bill-split payment requests, absence of an existing sent payment request is not proof that a participant is unpaid. Before any create_payment_request, fetch received Venmo transactions for each participant and mark paid only when sender email, amount in integer cents, and bill period/date/description corroborate the share; create requests only for the unpaid set.
[shr-00109] For file-based bill-split Venmo requests, convert every read-only fact into an executable guard before create_payment_request: assert the selected bill path comes from filtering the show_directory list with the target YYYY-MM regex and that exactly one candidate exists; assert show_file returns a dict with content and no message; assert duration and Total Amount regex matches are non-None; assert all phone and Venmo pagination pages are lists and fetch_failures == []; assert share arithmetic is exact or remainder is deterministically distributed. If any guard fails, call complete_task(status='fail') before creating any payment request.
[shr-00114] For bill-split Venmo requests, an empty unpaid set is a valid success. After paid-status and duplicate-request checks, if expected_unpaid == [], do not assert len(expected_unpaid) > 0; complete the task successfully with zero new requests.
[shr-00117] For file-based bill paid-status checks, define the payment window from the bill created_at/payment date (or payer payment date) through the current date, not from the service-period start, to avoid matching unrelated same-amount payments. If multiple same-amount received transactions remain ambiguous, require created_at >= bill created_at or description corroboration; if still ambiguous, fail/report.
[shr-00120] For artist-based most-played/most-liked information tasks, resolve the exact artist_id first, then paginate search_songs with artist_id and convert every read-only validation into an executable guard before answering: if any page is a dict with message or not a list, if fetch_failures is non-empty, if song_id values are not deduplicated, if the target artist_id is absent from a song's artists list, or if play_count/like_count is missing or non-numeric, call complete_task(status='fail') or raise before submitting an answer. Do not print validation failures and continue computing max/min from partial data.
[shr-00126] Create and maintain a checked_api_specs set per environment/task. Before the first call to any API in the current task—including apis.supervisor.show_account_passwords, apis.supervisor.complete_task, apis.spotify.login, apis.spotify.search_artists, apis.spotify.search_songs, apis.phone.send_text_message, and any library/detail API—call apis.api_docs.show_api_doc and record the app/api. If a call is attempted without a prior spec check, stop and inspect the spec first; do not rely on playbook examples, prior tasks, or memory. This operationalizes shr-00005/shr-00009 and prevents silent parameter/schema mistakes.

## COMMON MISTAKES AND CORRECT STRATEGIES

[cms-00010] Do not pass undocumented parameters such as access_token to APIs like show_song_reviews unless the API spec explicitly lists them. Use only documented parameters to avoid unnecessary failures, empty responses, or retries.
