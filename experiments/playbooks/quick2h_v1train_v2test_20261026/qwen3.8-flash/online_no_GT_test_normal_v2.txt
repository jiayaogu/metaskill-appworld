## APIs TO USE FOR SPECIFIC INFORMATION
[api-00004] You can use the "supervisor" app to get information about my accounts and use the "phone" app to get information about friends and family.

[api-00011] For Venmo friend tasks: phone.search_contacts returns contact objects with email, phone_number, and relationships; venmo.search_friends returns friend objects with email; venmo.add_friend returns a dict like {'message': 'Added to your friend list.'} on success.
[api-00015] apis.phone.search_contacts returns contact objects including contact_id, first_name, last_name, email, phone_number, and relationships; apis.venmo.search_friends returns friend objects including first_name, last_name, and email; apis.venmo.search_users can resolve a Venmo user/email by name when a contact email is missing or uncertain before calling apis.venmo.add_friend.
[api-00021] Simple Note/file_system export schemas: apis.simple_note.search_notes returns note metadata only (note_id, title, tags, created_at, updated_at, pinned); use tags=['habit-tracker'] for habit logs rather than relying only on query, and paginate. apis.simple_note.show_note returns a dict with a full 'content' string; parse that variable, not console output. apis.file_system.directory_exists returns {'exists': bool}; apis.file_system.create_file accepts '~/...' paths and returns {'message': ..., 'file_path': '/home/...'} with an absolute path; apis.file_system.show_file returns {'content': ...}. apis.supervisor.show_account_passwords returns a list of {'account_name': ..., 'password': ...}; apis.phone.send_text_message returns {'message': ..., 'text_message_id': ...}.
[api-00025] apis.file_system.show_file returns the file content and may have file_path=None; do not rely on show_file to verify the saved path. Use the response from apis.file_system.create_file, which returns the authoritative absolute file_path, for path verification, and use show_file only to verify content.

## COMMON MISTAKES AND CORRECT STRATEGIES

[cms-00010] Do not deduplicate or match people by only one identifier such as phone_number or email. Normalize and compare available identifiers (email, name, phone) when resolving contacts across apps, and verify the final state to avoid missing or duplicate entries.
[cms-00014] When collecting intended people from multiple relationship filters (e.g., coworker and friend), deduplicate by stable contact_id first; do not assume relationship-filtered contact lists are disjoint. Then match against existing Venmo friends using normalized email and normalized full name, treating email as preferred but allowing exact full-name match when email is missing/inconsistent.
[cms-00018] Never collapse Venmo identity checks into a single OR set of emails and names. If an intended contact has a valid/resolved email, that email must match an existing Venmo friend before marking them already added; a full-name match alone is only a fallback when the contact email is missing, invalid, or unresolved. Before mutating state, deduplicate intended contacts by contact_id and by normalized email/name, and only add contacts whose email has been resolved to a Venmo user.
[cms-00023] For note-to-CSV tasks: do not derive columns from search_notes order (newest/pinned first); sort by log date before parsing. Use tags=['habit-tracker'] instead of relying on query='habit'. Deduplicate by date (keep latest updated_at) and leave a cell blank if a habit is not present in that date's log. Do not use disallowed modules such as io (e.g., io.StringIO); build CSV text with string joins.
[cms-00028] When parsing structured notes, if the parser returns an empty result even though the raw content visibly contains matches, treat it as a parser bug rather than a data problem. Fix the parser to use the full API response variable and preserve original line indentation; never manually hardcode a few visible items from truncated console output as a fallback.
[cms-00029] For habit CSV exports, separate internal chronological ordering from output ordering: build habit_order from the earliest chronological log, but sort CSV rows according to the task requirement, such as descending dates for ~/backups/habit_log.csv. Do not let the ascending sort used to establish column order accidentally produce ascending output rows.
[cms-00031] Do not skip live API-doc checks for APIs that appear simple or already have playbook schemas, such as apis.supervisor.show_account_passwords, apis.simple_note.login, apis.file_system.show_file, and apis.file_system.create_file. After each call, validate against the documented success/failure schema: if a failure 'message' is present or expected success keys such as access_token, content, or file_path are missing, stop and fix before continuing.
