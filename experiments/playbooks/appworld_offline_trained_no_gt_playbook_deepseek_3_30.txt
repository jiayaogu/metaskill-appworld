## STRATEGIES AND HARD RULES
[shr-00001] Make sure to end code blocks with ``` followed by a newline(\n).
[shr-00005] Always look at API specifications (using apis.api_docs.show_api_doc) before calling an API.
[shr-00006] Write small chunks of code and only one chunk of code in every step. Make sure everything is working correctly before making any irreversible change.

[shr-00009] When combining data from multiple sources (like playlists), always: (1) handle pagination properly to ensure complete data collection, (2) use set operations to avoid duplicate entries, and (3) verify API responses at each step before proceeding.
[shr-00011] Always verify API response schemas before implementation to ensure required data fields are available. When encountering errors, systematically check documentation to identify the correct API endpoint for the needed functionality.
[shr-00013] When working with APIs, verify exact field names in response schemas rather than making assumptions. Common variations include 'id' vs '[type]_id' (e.g., 'song_id'), and boolean flags like 'liked' vs 'is_liked'.
[shr-00016] For rating/review systems: (1) Always check if a review already exists before attempting to create a new one, (2) Be prepared to handle both creation and update cases, (3) Verify the exact API endpoints for checking existing reviews versus creating new ones.
[shr-00019] When filtering transactions by specific criteria (like roommates), always verify the actual transaction data to confirm whether any matches exist before attempting modifications. The absence of matching transactions is a valid outcome that should be handled gracefully.
[shr-00020] For tasks involving specific relationships (siblings, roommates, etc.): (1) First verify the existence of such relationships in the contact list using the phone app, (2) Only proceed with dependent actions if relationships are confirmed to exist, (3) Handle the absence of relationships gracefully as a valid outcome.
[shr-00022] When matching identities across different systems (e.g., Phone contacts to Venmo transactions): (1) Always verify the exact identifier fields used in each system's API response schema, (2) Never assume fields will match across systems (phone numbers vs emails), (3) Use the correct matching field from each system's documentation.
[shr-00024] When working with multiple API endpoints from the same service, never assume field name consistency - always verify the response schema for each endpoint individually, as keys like 'id' vs '[type]_id' may vary.
[shr-00027] When handling API responses from the same service, implement flexible field name resolution (e.g., song.get('song_id', song.get('id'))) to account for inconsistent naming conventions across endpoints.
[shr-00029] For long-running tasks involving multiple API calls: (1) Implement token refresh logic proactively, (2) Store initial credentials securely to enable re-authentication, (3) Monitor for 401 errors and automatically re-authenticate when detected.
[shr-00031] When parsing unstructured data (notes, messages, etc.): (1) Always verify raw content alongside parsing logic, (2) Implement flexible parsing that can handle formatting variations, (3) Test parsing with sample data before full implementation.
[shr-00033] When parsing multi-line note formats: (1) Track the current item being processed across line breaks, (2) Implement stateful parsing that maintains context between lines, (3) Validate parsed results against known patterns in the raw content to ensure all relationships were captured correctly.
[shr-00036] For date-based transaction filtering: (1) Always calculate date ranges precisely (including today when specified), (2) Format dates in the exact format required by the API (YYYY-MM-DD), (3) Verify the date filtering works by checking sample transactions before full processing.
[shr-00038] For payment processing tasks: (1) Always verify sender identities against authoritative contact sources before processing transactions, (2) Calculate date ranges precisely including boundary conditions when specified (e.g., 'including today'), (3) Process all pages of transaction results, (4) Verify API responses at each modification step before proceeding.
[shr-00040] For recommendation analysis tasks: (1) Always collect complete recommendation data by handling pagination properly, (2) Use counting mechanisms (like defaultdict) to track item frequencies, (3) Verify the minimum/maximum counts before finalizing results.
[shr-00042] When collecting song IDs from different Spotify endpoints (library vs playlists vs albums), be aware that field names may differ: (1) Library songs use 'song_id', (2) Playlist and album songs use 'id'. Always verify the exact field name in each endpoint's response schema before implementation.
[shr-00045] When comparing temporal data across multiple sources: (1) ensure complete data collection from all relevant sources, (2) verify date formats are consistent before comparison, (3) use proper comparison functions (like min() with datetime strings), and (4) handle potential ties in temporal comparisons by implementing secondary sorting criteria if needed.
[shr-00048] When working with payment/transaction APIs across different services, never assume parameter naming consistency - always verify the exact parameter names in documentation. Common variations include 'recipient_email' vs 'user_email' for identifying payment recipients.
[shr-00050] For payment reconciliation tasks: (1) Always verify the source data (notes) against transaction records, (2) Use precise filtering to identify unpaid individuals, (3) Handle personal data carefully when sending payment requests, (4) Verify API response schemas before implementation to ensure required data fields are available.
