[shr-00009] When synchronizing contacts between services, always use email addresses as the primary matching criterion. This provides the most reliable way to identify the same person across different platforms.
[shr-00012] Always verify API response schemas in documentation before accessing fields. Different APIs may use different naming conventions for similar concepts (e.g., 'id' vs 'song_id').
[shr-00016] When making authenticated API calls, maintain a checklist of all required authentication tokens for each step of your workflow. Verify each call includes the correct token before execution.
[shr-00018] When implementing skip/next operations (like skipping songs), always include a reasonable maximum limit to prevent infinite loops in case the target condition is never met.
[shr-00020] When calling APIs, always verify the exact parameter names in the documentation. Different APIs may use different naming conventions for similar parameters (e.g., 'path' vs 'directory_path', 'source_path' vs 'source_file_path'). Never assume parameter names based on similar APIs.
[shr-00022] When parsing semi-structured data (like notes with inconsistent formatting): (1) Implement primary parsing logic for the expected format, (2) Include validation checks on parsed results, (3) Always implement fallback mechanisms (either manual inspection or alternative parsing methods) when validation fails.
[shr-00024] For file system operations, always verify exact parameter names in API documentation. Common file system API parameter naming patterns include: (1) 'directory_path' for directory operations (not 'path'), (2) 'source_file_path' and 'destination_file_path' for file moving (not 'source_path'/'destination_path')
[shr-00026] When calculating financial transaction totals: (1) Always use date filtering parameters (min_created_at/max_created_at) to scope to the correct time period, (2) Verify the direction parameter ('sent' vs 'received') matches the analysis goal, (3) Implement pagination with while True loop to ensure complete data collection across all pages.
[shr-00029] When matching data across different systems: (1) Always examine sample data formats from all sources first, (2) Implement and test matching logic with small samples before scaling, (3) Build parsing that handles expected format variations (e.g., splitting 'title by artist' strings), and (4) Verify API response structures through documentation before coding.
[shr-00032] When matching music content: (1) Normalize strings (lowercase, trim whitespace) before comparison, (2) Implement flexible matching that accounts for partial matches and variations in artist formatting, (3) Compare only essential parts (song titles) when matching against a reference list.
[shr-00034] When modifying music queues: (1) Always clear the existing queue first to ensure a clean state, (2) Verify the queue is empty before adding new items, (3) When adding recommendations, process them as a batch to maintain atomicity.
[shr-00037] Never assume API names based on intuitive naming - always verify the exact API name in documentation before calling it. Common naming patterns (like 'send_payment') may not match the actual API name (e.g., 'create_transaction').
[shr-00038] When splitting shared expenses: (1) Always verify the complete list of participants first by checking all relevant contacts, (2) Calculate shares precisely before executing transactions, (3) Use the correct API for each transaction type (payment requests vs direct payments), and (4) Include clear descriptions in all transactions for auditability.
[shr-00040] When working with payment APIs, be aware that different transaction types (direct payments vs payment requests) may use different parameter names for similar concepts (e.g., 'receiver_email' vs 'user_email'). Always verify the exact parameter names for each specific API endpoint.
[shr-00042] When working with music release dates across different services: (1) Always verify the date format in API responses (YYYY-MM-DD vs MM/YYYY), (2) Implement consistent formatting for storage (preferably MM/YYYY for readability), (3) Handle potential mismatches between API date formats and your storage format with conversion logic.
[shr-00044] When processing semi-structured notes with incomplete data: (1) Look for explicit markers (like 'TODO') to identify incomplete entries, (2) Implement targeted string matching rather than broad parsing when dealing with known format patterns, (3) Preserve all existing formatting when making updates by replacing exact string patterns rather than reconstructing content.
[shr-00046] For music metadata tasks: (1) Always verify the date format specifications in API documentation before processing, (2) Implement consistent date formatting for storage (preferably MM/YYYY for readability), (3) Include conversion logic to handle mismatches between API date formats and your storage format.
[shr-00047] When updating structured data in notes: (1) Parse existing content carefully to identify incomplete entries, (2) Use authoritative external APIs to verify/fill missing information, (3) Preserve original formatting by replacing exact string patterns rather than reconstructing content, (4) Implement validation checks before applying updates.
[shr-00049] When creating modified versions of existing notes: (1) Always retrieve and verify the template note first to ensure correct formatting, (2) Make targeted modifications while preserving the original structure and other content, (3) Verify the creation of the new note matches expectations by comparing against the template.
